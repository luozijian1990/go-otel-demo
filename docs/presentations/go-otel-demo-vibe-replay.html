OVERVIEW

一句话定位 + 核心机制

go-otel-demo
// 一句话
本地一键起一整套"生产级可观测性最小骨架"——4 个 Go 服务 + 网关 + Collector + Jaeger + UI，点一个按钮就触发一条横跨 HTTP / MySQL / Redis / RabbitMQ / 多跳调用的真实 trace，用 TraceId 在 Jaeger 里精准还原"哪一跳挂了 / 哪一跳慢了"。
// 核心机制（最不显然、最值钱的设计）
Collector 的 tail sampling 策略——5xx / span ERROR / >3s 慢请求 100% 保留，其余正常请求只留 1%。这一条把整个项目从"trace 玩具"升级成"可拿来讲故障排障的演练台"。 配合全链路把 TraceId 回吐给用户（响应 header X-Trace-Id + 错误 JSON 体 + Traefik access log），完成了 用户看 5xx → 拿 TraceId → 一条命令分析根因 的闭环。
// 技术栈
Go · Gin GORM go-redis amqp091 OpenTelemetry SDK otelgin / otelhttp otelgorm / redisotel OTLP gRPC OTel Collector Contrib Jaeger all-in-one Traefik v3 Docker Compose Python 3 (零依赖)

★ STEP 03 · CLIMAX

为什么"采样在 Collector，不在 SDK"

~1300 字 / 约 5.5 分钟
// 问题陈述
生产环境每秒几千条 trace，全存进 Jaeger 几小时就爆。但如果在 SDK 端按 1% 概率丢，线上 5xx 告警的 trace 大概率被丢——你要 debug 时打开 Jaeger 看不到。
// 解法
把采样决策推迟到 trace 完整收齐之后。Collector 在内存里缓 trace，等同一 traceId 的 span 都到了，再根据"这条 trace 有没有 5xx / ERROR / 慢"决定保不保留。
// 这一招的代价
Collector 要吃内存（缓 trace）；要等 decision_wait（这里 10s）；晚到的 span 会被丢弃。生产里这两个参数要按 P99 trace duration 和 QPS 调。
采样策略矩阵
HTTP 5xx old100%
HTTP 5xx new100%
span status = ERROR100%
latency > 3000ms100%
其余正常请求1%
// 撬动语义
30 行 yaml → 把整个 demo 从
"trace 玩具" 拉到 "排障演练台"
