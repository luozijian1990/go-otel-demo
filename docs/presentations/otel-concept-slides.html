04 / 13
TRACE

Trace 是树,Span 是树上的每一段

例:GET /chain/mysql/error
📷
截图占位 · Jaeger trace tree
assets/jaeger-chain-trace.png
①
Trace = 一次完整请求,有唯一 traceId。上图整棵树就是一个 trace。
②
Span = 其中一段工作(一次 HTTP 处理、一次 SQL、一次 Redis 调用),是树上的一个节点。
③
每个 span 记着 parentId,父子关系拼出树;缩进越深 = 调用越往下游。
④
span 的长度就是耗时 —— 一眼看出"哪一段最长";红色那段就是出错的地方。
// 一句话
看日志是"逐行读流水账",看 trace 是"一张 X 光片"。

05 / 13
SPAN

一个 span 长这样(SDK 自动产出,没手写一行)

console span// SDK 把 span 直接打到控制台的样子 { traceId: '7fcccd0a...eddc544', parentId: 'a1b2c3d4e5f60718', name: 'GET /chain/mysql/error', id: '188af03d8d92b148', kind: 1, // SERVER timestamp: 1688624928628000, duration: 41200, // 微秒 attributes: { 'http.method': 'GET', 'http.route': '/chain/mysql/error', 'http.status_code': 500 }, status: { code: 2, message: 'ERROR' }, events: [ { name: 'exception', ... } ], links: [] }
id
traceId 同一请求都一样;id/parentId 拼父子。
⏱
timestamp+duration = 在哪开始、跑了多久。
🏷
attributes = 标签键值对(方法/路由/状态码/SQL...),查询和过滤全靠它。
●
status = ERROR 让这条 span(及整条 trace)被重点保留 —— 后面采样会用到。
⚡
events 里挂着 exception 堆栈等"时刻点"。
// 注意
上面是 Node 控制台示例,字段是 OTel 通用的;我们 demo 里 Go 服务的 span 字段一模一样。

PROPAGATION

traceId 顺着 HTTP header 往下游传

▸
标准叫 W3C Trace Context,那个 header 就是 traceparent —— 所有现代 SDK 默认认它。
▸
反问:如果中间某个服务把 header 弄丢了? 答:从那一跳起断链,会冒出一条新 trace,根因就拼不全了。
▸
我们 demo 里 Traefik 网关的 access log 也记了这个 TraceId,拿着它能直接跳进 Jaeger。

07 / 13
★ OPENTELEMETRY

OTel 是"产数据的标准",不是存数据的后端

// 一句话
OpenTelemetry = 一套规范 + 各语言 SDK + Collector 工具,厂商中立。它干的事只有一件:用统一格式,标准化地产出遥测数据(traces/metrics/logs)。
OTel 负责 · 产出 & 搬运

埋点 → 标准化 → 发出去

SDK 自动产 span;按 OTLP 协议把数据发走。换后端不用改业务代码。

后端负责 · 存储 & 可视化

Jaeger / Zipkin / Prometheus / 云

收下数据,存起来,画成你能查的界面。这些不是 OTel,是 OTel 的"消费者"。

// 最常见的误解
"OTel 是不是又一个 Jaeger / Prometheus?" —— 不是。 Jaeger 是后端,OTel 是给所有后端供数据的统一上游。
// 它解决的痛
以前换个追踪系统就要把埋点重写一遍。OTel 把"怎么埋点"和"用谁来看"解耦了:埋一次,后端随便换。

DATA FLOW

SDK → Exporter → OTLP → Collector → 后端

▸
Exporter = SDK 里负责"把数据发出去"的组件;默认格式就是 OTLP(OpenTelemetry Protocol)。
▸
OTLP 走 gRPC 或 HTTP;为省网络开销,会 Batch 攒一批 span 一起发。
▸
应用其实也能直连后端,但那样每个服务都得各配一遍 —— 所以中间加一个 Collector 统一收。

09 / 13
COLLECTOR

一个与厂商无关的"遥测数据中转站"

// 为什么要它
把"收数据 / 处理数据 / 发去哪"从每个应用里抽出来,集中到一处管理 —— 应用只管按 OTLP 发给 Collector,采样、改标签、换后端都在 Collector 上调,不用动业务代码。
① Receiver 接收器

数据怎么进来(如 otlp)。至少配一个。

② Processor 处理器

中间怎么加工:batch 批处理、tail_sampling 采样、改/删标签。可选但常用。

③ Exporter 导出器

数据发去哪(如 otlp/jaeger)。至少配一个。

④ Connector / Extension

连接两条管道 / 健康检查等辅助。入门可先不管。

部署形态跑在哪适合
Agent 代理和应用同主机
(sidecar / daemonset)		新应用 / K8s
Gateway 网关独立服务,
每集群/区域一组		已有应用
集中治理
// 关键规则(下一页验证)
配了组件 ≠ 启用。必须在 service.pipelines 里引用,它才真正生效。

10 / 13
CONFIG

三段组件 + 一条 pipeline 把它们串起来

本仓库真实配置
otel/collector.yamlreceivers: otlp: protocols: grpc: { endpoint: 0.0.0.0:4317 } # Go 服务上报入口 http: { endpoint: 0.0.0.0:4318 } processors: tail_sampling: { ... } # 见下一页 batch: { timeout: 2s } exporters: otlp/jaeger: { endpoint: jaeger:4317 } debug: { verbosity: basic } service: pipelines: traces: receivers: [otlp] processors: [tail_sampling, batch] exporters: [otlp/jaeger, debug]
in
receivers.otlp 开了 4317(gRPC)和 4318(HTTP)两个口子收数据。
mid
processors 先采样、再批处理(细节下一页)。
out
exporters 一份发 Jaeger,一份打到 Collector 日志方便调试。
★
service.pipelines.traces 才是开关:把上面三段引用进来,组件才真正上线。
// 顺序有讲究
processors 是有序的:tail_sampling 必须排在 batch 前面,否则采样决策可能不对。

SAMPLING

错误 / 慢 100% 留,正常只留 1%

tail_sampling
5xx / ERROR · 必留
慢 >3s · 必留
正常 · ~1%
正常 · 丢弃
总数: 100
保留: 3
丢弃: 97
→ 关键 trace 0 丢失
// 为什么是"尾部"采样
tail = 等整条 trace 的 span 基本到齐,再回头看"它出错了吗 / 它慢吗",然后决定留不留。 如果在 SDK 端按 1% 概率瞎丢,一条 error 也只有 1% 概率被留下 → 99% 丢失关键证据;尾采样把它翻成 100% 留。
